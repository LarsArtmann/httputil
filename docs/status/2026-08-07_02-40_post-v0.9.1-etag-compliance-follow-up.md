6. **Multiple `If-None-Match` headers combined** (`etag.go:222-224`) — `matchesIfNoneMatch` now uses `strings.Join(req.Header.Values(headerIfNoneMatch), ", ")` instead of `req.Header.Get(...)`. Committed `256ccba`.

### Q2: Should the `etagWriter.flush()` silent error swallow be fixed now or deferred?

`etag.go:175`: `_, _ = w.ResponseWriter.Write(w.body)` silently ignores errors on the final body write. Every other write path in `etagWriter` classifies errors via `errorfamily.WrapTransient(ErrCodeETagWriteFailed)`, but this path (the normal flush, not the streaming-after-overflow path) does not. The fix is ~5 lines: capture `n, err`, wrap if `err != nil`. The question is whether this is a behavior change worth a dedicated fix or should be batched with other `etagWriter` improvements. The error is already lost in production today, so fixing it only adds observability, not correctness.

### Q3: Is the `matchesIfNoneMatch` change a behavior change that needs a CHANGELOG entry under "Changed" rather than "Fixed"?

The old code used `req.Header.Get(headerIfNoneMatch)` which returns only the first value when multiple `If-None-Match` headers are present. The new code uses `strings.Join(req.Header.Values(...), ", ")` to combine all values. This is strictly more correct (RFC 9110 §5.2), but it IS a behavior change: a client sending two `If-None-Match` lines where only the second matches would previously get 200 and now gets 304. In practice, multiple `If-None-Match` headers are extremely rare (most clients send a single header with a comma-separated list), so the impact is negligible. I classified it as "Fixed" in the CHANGELOG. Should it be "Changed" instead?
