The coupling blocker The previous review (2026-07-26) correctly identified that extracting compression into a public sub-package creates a circular import: compression.go returns Middleware (defined in root), and the compress writer uses responseWrapper and ErrCode* (also in root). A public sub-package would need to import root for these types — while root re-exports compression types. That is a cycle.

03The Folder Question: Three Options Analyzed

"Should more folders be added?" decomposes into three distinct structural options. Each has radically different tradeoffs. The evidence — not aesthetic preference — decides.

A. Public Sub-Packages

REJECTED — circular imports

  • httputil/compression/, httputil/cors/, etc.
  • Compression depends on Middleware, responseWrapper, ErrCode* from root
  • Root must re-export compression types for consumers
  • = circular import, structurally impossible
  • Also breaks flat import ergonomics (httputil.CORS() → httputil/cors.CORS())
  • Confirmed rejected 2026-07-26 — still valid

B. Status Quo (Flat)

RECOMMENDED — Go-idiomatic

  • One import: httputil.Compression()
  • Internal symbols stay unexported
  • Matches Go stdlib precedent (net/http = 50+ files flat)
  • 33 files is navigable — well-named, IDE-friendly
  • No breaking changes, no complexity added
  • New middleware adds zero coupling (proven by last 3 features)
  • Project approaching v1.0 — stability over reorganization

C. Internal Packages

VIABLE but defer — marginal payoff

  • httputil/internal/compress/ — 6 impl files
  • httputil/internal/responsewrap/ — wrapper.go
  • httputil/internal/errcodes/ — error constants
  • Public API stays flat: httputil.Compression() unchanged
  • Root → internal is one direction: no cycles
  • Root goes from 33 → ~25 non-test files
  • Cost: ~15-20 files modified, types become internal-exported
  • Benefit: 8 fewer root files, better encapsulation
Why not internal/ now? Option C is the only folder structure that avoids circular imports while preserving the flat public API. But the payoff is marginal: 8 fewer root files in exchange for 3 new internal packages, ~15-20 files modified, and previously-unexported types that must be capitalized (exported) within internal/. The Go stdlib net/http package — with 50+ files — does not do this. Defer until after v1.0; revisit if root exceeds ~50 non-test files.

Multi-module split: STRONGLY REJECTED

A Go utility library must have a single go.mod. Multiple modules force consumers to go get each sub-module separately, create version drift risk, and provide zero composability payoff for a cohesive HTTP utility library. The Middleware type alias is the unifying abstraction — every middleware composes through it. Splitting modules would fragment this universal interface.
