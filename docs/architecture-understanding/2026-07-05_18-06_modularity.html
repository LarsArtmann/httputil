01Structure & Dependency Direction

github.com/larsartmann/httputil ├── net/http (stdlib) ├── log/slog, crypto/rand, compress/* (stdlib) └── github.com/larsartmann/go-error-family (same author, 0 transitive deps) github.com/larsartmann/httputil/httpspec └── net/http, net/http/httptest, testing (stdlib only — NO dependency on parent package)

The dependency graph is a strict tree pointing only at stdlib and one same-author library. depguard enforces this at lint time — no third-party imports can sneak in. Critically, the httpspec subpackage depends only on stdlib; it validates any http.Handler, so it is reusable far beyond this library.

02Coupling Assessment

Composability score: Excellent

Consumer Handler→ Recovery→ Logging→ Timeout→ Your Handler

Every middleware shares one signature — func(http.Handler) http.Handler — so any of them composes with any other, in any order, with zero adapters. Chain() and MiddlewareStack are thin orchestrators over this universal interface. This is the highest-composability design available in Go HTTP.

Single flat package — deliberate tradeoff, watch the size

All 28 root files live in one httputil package. Benefit: one import (httputil.CORS, httputil.ETag), no subpackage spelunking. Cost: the package surface is large and will grow. This is the correct tradeoff for a utility library — consumers want flat ergonomics, not a deep package tree. But at 28 files it is approaching the point where grouping (e.g. an internal compress/ for the 7 compression files) would aid navigation without breaking the public import path. Not urgent; track it. (Update 2026-07-26: the compress/ split was evaluated and rejected — compression files depend on root symbols (Middleware, responseWrapper, ErrCode*), so extracting them creates a circular import. The flat layout is structural, not a debt item. Root package now has 62 files.)

03Service-Orientation Roadmap

The library already practices service-orientation at its extension seams — three pluggable interfaces let consumers inject their own implementations without forking:

Interface Default impl Service it abstracts
RateLimiter TokenBucketLimiter (in-memory) Rate-limit store (swap in Redis/Memcached)
MetricsRecorder none (consumer supplies) Metrics sink (Prometheus, OTel, Datadog)
WriterFactory gzip/deflate Compression backend (brotli, zstd — no core dep added)
1

Keep extension points interface-minimal

Each has exactly one method — the ideal size. Resist adding convenience methods; let adapters compose.

2

Address the unbounded-memory RateLimiter

TokenBucketLimiter grows its key map without eviction. For production per-IP limiting, document that a custom RateLimiter with eviction (or TTL) is required — or add an optional TTL to the default.

3

Consider an internal split for compression

The 7 compression files are a cohesive subsystem; an internal compress folder (unexported) would reduce root-package noise while preserving the flat public API.
