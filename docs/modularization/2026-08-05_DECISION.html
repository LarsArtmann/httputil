Modularization Decision

Should httputil split into multiple Go modules, sub-packages, or internal packages? Decision: single module, flat package. The structure is correct and Go-idiomatic.

01Verdict

FLAT PACKAGE CONFIRMED — User decision 2026-08-05 (ergonomics)

The user reviewed the three options and selected the flat structure based on ergonomics: for a middleware library where everything shares one signature (func(http.Handler) http.Handler), a single import path (httputil.CORS()) is the right API. Fragmented sub-package namespaces (httputil/cors.CORS()) add friction with zero composability gain.

Multi-module (separate go.mod): Rejected. A library needs one import path.

Public sub-packages: Rejected. Creates circular imports: compression depends on root (Middleware, responseWrapper, ErrCode*), root re-exports compression types. Confirmed 2026-07-26, still valid.

Internal packages: Technically viable but deferred. The only folder structure that avoids cycles while preserving the flat public API. Payoff is marginal (8 fewer root files). Defer until post-v1.0 or if root exceeds ~50 non-test files.

05The Internal/ Option (Deferred)

The only folder structure that avoids circular imports while keeping the flat public API. If pursued post-v1.0, the target structure would be: 

httputil/
├── compression.go          (public API stays in root)
├── etag.go                 (public API stays in root)
├── cors.go, csrf.go, ...   (all middleware stays in root)
├── recorder.go             (Middleware type, Chain, ResponseRecorder)
├── internal/
│   ├── responsewrap/       (responseWrapper, hijackDelegate, flushDelegate)
│   ├── errcodes/           (ErrCode* constants + message templates)
│   └── compress/           (compressWriter, negotiator, qvalue, pool, content_type)
│       ├── writer.go
│       ├── writer_compress.go
│       ├── pool.go
│       ├── negotiator.go
│       ├── qvalue.go
│       └── content_type.go

Dependency flow (no cycles)

root (compression.go, etag.go, recorder.go)
  └─→ internal/responsewrap/
  └─→ internal/errcodes/
  └─→ internal/compress/
        └─→ internal/responsewrap/
        └─→ internal/errcodes/

All arrows point downward (root → internal). No package imports its parent. Previously unexported types become exported within internal/ (e.g. responsewrap.Wrapper, compress.Writer) but invisible to external consumers.

Why defer Cost: ~15-20 files modified, 3 new internal packages, tests split across 4 packages, error code constants duplicated or moved. Benefit: 8 fewer root files (33 → 25). The Go stdlib net/http (50+ files) does not use this pattern. Defer until the cost/benefit ratio shifts — either root exceeds ~50 files or the compression subsystem grows significantly.

06Conditions to Revisit

Trigger Action
Root package exceeds ~50 non-test files Re-evaluate internal/compress/ extraction

A second cohesive subsystem emerges with 5+ implementation files Extract both to internal/ packages
v1.0 stability commitment is shipped Revisit as a post-stability structural improvement
Consumer requests finer-grained imports Re-evaluate public sub-packages (unlikely for a middleware library)
Architectural decision recorded The flat single-module structure is the deliberate, Go-idiomatic choice for this library. It is not a debt item. The internal/ option exists as a future improvement path if the trigger conditions are met.
