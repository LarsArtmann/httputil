01Honesty Issues

High · Lying name

RequestIDConfig.ForwardHeader names the wrong direction

requestid.go:17 — field; used at :60 as the request READ header

ForwardHeader reads as "the header we forward out," but the code uses it as the incoming header to read a propagated ID from (req.Header.Get(cfg.ForwardHeader)). The outgoing response header is the separate HeaderName field. A reader trusts "Forward" = outbound and is misled. HeaderName is also vague — "which header?"

Better names (v1): IncomingHeader (the request header read) and OutgoingHeader or ResponseHeader (the response header written). Direction becomes self-evident.
Low · Fixed

ReadyHandler doc implied an override that doesn't exist

health.go:40 — comment

The doc said "Override with a custom handler that checks database connections" but ReadyHandler() takes no arguments and always returns up. Fixed: the comment now tells the user to register their own handler at /health/ready instead.

03Glossary — no split-brain terminology

One concept = one name (consistency win)

The codebase uses a single, consistent vocabulary throughout. No synonym drift was found:

  • Middleware — always Middleware / func(http.Handler) http.Handler, never "interceptor", "filter", "wrapper".
  • Config — every options type ends in Config; every constructor is Default*Config().
  • Validate — one method name for startup checks across all configs.
  • Factory — WriterFactory, GzipWriterFactory, DeflateWriterFactory — consistent factory naming.
  • Recorder / Wrapper / Writer — three distinct roles, three distinct names, never conflated.
