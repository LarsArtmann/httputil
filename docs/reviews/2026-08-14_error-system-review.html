Toward a Typed, Hierarchical Error System

A review of how httputil creates, classifies, and propagates errors today, and a concrete design for making them type-safe, hierarchical, and fully leverage github.com/larsartmann/go-error-family.

01 Current State

The project already uses go-error-family for behavioral classification (Transient, Infrastructure, Rejection, Orchestration) at runtime error sites. However, configuration-validation errors are still plain stdlib sentinels wrapped with fmt.Errorf, and error codes are raw strings.

02 Problem Catalog

Critical

P1 — Validation errors are plain stdlib sentinels

Every config Validate() method defines unexported var err* = errors.New(...) sentinels and wraps them with fmt.Errorf("%w: ..."). The resulting errors are not classified, not coded, and not contextual. Callers can only match them by fragile string comparisons.

Fix: define package-level errorfamily.NewRejection / NewInfrastructure sentinels with machine-readable codes, then clone them with context in each validation branch.

High

P2 — Error codes are stringly-typed constants

ErrCodeWriteFailed = "http.write_failed" is a raw string. Nothing prevents a typo or mixing a CORS code into a compression site. The codes have no compile-time grouping or hierarchy.

Fix: introduce a branded type Code string and domain-grouped typed constants. Provide a Code.Domain() method to extract hierarchy at runtime.

Medium

P3 — Public APIs return bare error

Validate() error, Shutdown() error, and Add() error discard static type information at the signature level. Callers must rely on interface assertions at the call site.

Fix: keep error signatures for backward compatibility in v0.x, but guarantee that every returned value implements Coded, Classified, and Contextual. Consider concrete return types for a future v1.

Low

P4 — Intentionally-swallowed writes are scattered

After HTTP headers are committed, write failures cannot be reported to the caller. The codebase uses _, _ = w.Write(...) at multiple sites with inline comments. This is correct but noisy and easy to misread as a bug.

Fix: centralize the pattern in a single writeCommittedBody helper whose name and docstring make the intentional swallow explicit.

High

P5 — erraudit is being run with a mismatched policy

The command --enforce-samber-oops flags every errors.New and fmt.Errorf as a violation, even though the project deliberately uses go-error-family. This produces 61 false-positive-looking findings and distracts from the real gaps.

Fix: run erraudit without the samber/oops flag, or add a project erraudit config that reflects the actual library choice. The goal is consistent classification, not a dependency swap.

03 The Vision

  • Every exported error value is coded, classified, and contextual.
  • Configuration mistakes produce Rejection errors with the offending field, value, and invariant attached.
  • Runtime HTTP failures produce Transient or Infrastructure errors with the underlying cause preserved.
  • Error codes form a hierarchy: http.*, cors.*, csrf.*, compression.*, server.*, etc.
  • Callers use errors.AsType[errorfamily.Coded] instead of string matching.
  • No raw errors.New or fmt.Errorf for domain errors; only for genuine stdlib bridge points.

04 Go Data Model

The new model builds on the existing go-error-family foundation. It adds a typed code constant, domain extraction, and a centralized validation-error constructor. 

// Code is a typed error code. It prevents accidental mixing of codes across domains.
type Code string

// Domain returns the hierarchical domain prefix of a code.
// Example: Code("cors.negative_max_age").Domain() == "cors".
func (c Code) Domain() string {
    if i := strings.Index(string(c), "."); i >= 0 {
        return string(c[:i])
    }
    return "http"
}

// Domain-grouped, typed codes.
const (
    // HTTP layer
    CodeWriteFailed         Code = "http.write_failed"
    CodeHijackUnsupported   Code = "http.hijack_unsupported"
    CodeHijackFailed        Code = "http.hijack_failed"
    CodeCompressWriteFailed Code = "http.compress_write_failed"

    // CORS
    CodeCORSCredentialsWithAllOrigins Code = "cors.credentials_with_all_origins"
    CodeCORSNegativeMaxAge          Code = "cors.negative_max_age"

    // Server
    CodeServerAddrEmpty       Code = "server.addr_empty"
    CodeServerShutdownFailed    Code = "server.shutdown_failed"
    CodeServerTLSMinVersion   Code = "server.tls_min_version_insecure"
)

// Backward-compatible string constants.
const (
    ErrCodeWriteFailed = string(CodeWriteFailed)
    // ...
)

// newConfigError builds a classified, contextual validation error.
func newConfigError(code Code, config, field, value, rule string) *errorfamily.Error {
    return errorfamily.NewRejection(string(code), config+"."+field+" "+rule).
        WithContextMap(map[string]string{
            "config": config,
            "field":  field,
            "value":  value,
            "rule":   rule,
        })
}

05 Composition in Action

Converting a config validator from stdlib sentinels to classified errors removes string wrapping and attaches structured context in one move.

Before: stdlib sentinel
var errNegativeMaxAge = errors.New("CORSConfig: MaxAge must not be negative")

func (c CORSConfig) Validate() error {
    if c.MaxAge < 0 {
        return fmt.Errorf("%w: got %d", errNegativeMaxAge, c.MaxAge)
    }
    return nil
}
After: classified + contextual
var errCORSNegativeMaxAge = errorfamily.NewRejection(
    string(CodeCORSNegativeMaxAge),
    "CORSConfig.MaxAge must not be negative",
)

func (c CORSConfig) Validate() error {
    if c.MaxAge < 0 {
        return errCORSNegativeMaxAge.WithContext("value", strconv.Itoa(c.MaxAge))
    }
    return nil
}

The new value is a *errorfamily.Error, so callers can do type-safe matching: 

coded, ok := errors.AsType[errorfamily.Coded](err)
if ok && coded.ErrorCode() == string(CodeCORSNegativeMaxAge) {
    // handle specific CORS config failure
}

06 Validation Layer

With the new model, an invalid config is not a generic string. It is a Rejection error carrying the exact invariant that was violated. The type system does not make invalid states unrepresentable (configs are still structs), but the error model makes them diagnosable.

Example output

[rejection:cors.negative_max_age] CORSConfig.MaxAge must not be negative: value=-10

Consumers can extract the code, family, and context map without parsing strings.

The hierarchy is encoded in the code string. A small helper makes it queryable: 

func DomainOf(err error) string {
    coded, ok := errors.AsType[errorfamily.Coded](err)
    if !ok {
        return "unknown"
    }
    return Code(coded.ErrorCode()).Domain()
}

07 Decision Log

Keep go-error-family; do not adopt samber/oops

Switching would add a dependency, lose the family-classification model, and force a rewrite of 35+ call sites. The project already owns a library purpose-built for classified errors; the fix is consistency, not a swap.

Keep error return signatures in v0.x

Changing Validate() error to Validate() *errorfamily.Error is a breaking API change. Because *errorfamily.Error implements error, callers still receive a classified value. The report recommends concrete returns only for new internal APIs or a future v1.

Use dot-notation codes for hierarchy

A typed Code plus a Domain() method gives a hierarchy without introducing a heavy tree of custom types. It is simple, inspectable, and serializable.

Package-level sentinels with per-instance context

This satisfies the project's err113 rule (no inline errors.New) while avoiding repeated allocations. WithContext clones the sentinel safely.

Ignored post-header writes are intentional

Once headers are committed, a write error cannot be surfaced. The recommendation is to centralize the swallow pattern, not to "fix" every site by returning an error that cannot be acted upon.

08 Anti-Patterns

Do not invent a parallel error tree

Adding a custom httputil.Error interface that duplicates Coded + Classified + Contextual fragments the protocol. Use the interfaces from go-error-family directly.

Do not switch to samber/oops just to silence erraudit

That would replace one set of tool warnings with a different error model that does not match the project's classification needs.

Do not use unexported sentinels as the public matching API

Consumers need exported codes or typed predicates. Keep sentinels unexported if desired, but expose the Code constants and document them.

09 Migration Roadmap

1

Introduce typed Code and domain helpers in errors.go

Keep existing string constants for backward compatibility. Add the Code type, typed constants per domain, and Domain() / DomainOf().

2

Convert one middleware at a time

Start with cors.go or server.go: replace errors.New sentinels with package-level errorfamily.New* sentinels and update Validate() branches to clone with context.

3

Add tests that assert classification

For every validation error, add a test verifying it implements Coded, Classified, and Contextual and that the code matches the expected typed constant.

4

Register templates for new config error codes

Extend RegisterErrorClassifications() so the user-facing what/why/fix/escape messages are available through the error family registry.

5

Centralize intentional write swallows

Replace scattered _, _ = w.Write(...) sites with a documented helper such as writeCommittedBody.

6

Update project erraudit configuration

Remove or neutralize the --enforce-samber-oops flag. Align erraudit with go-error-family so warnings reflect actual project policy.

7

Document the error model in AGENTS.md

Add a section explaining how errors are classified, how codes are grouped by domain, and how consumers should match them.

10 Conclusion

The project is not starting from zero. It has a solid classification library and already uses it at runtime error boundaries. The missing layer is the configuration-validation surface: errors there are still plain strings, unexported, and unclassified.

The best next step is to bring every config validator into the same model: typed Code constants, package-level classified sentinels, and contextual clones. That gives a typed, hierarchical error system without adding dependencies or breaking the public API.

Bottom line: fully adopt the library you already have.
