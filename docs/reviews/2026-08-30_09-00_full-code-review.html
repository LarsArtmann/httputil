00Summary

The review executed the Pareto plan at docs/planning/2026-08-30_08-00_full-code-review-execution-plan.html: source files reviewed directly by component tier, test files given a delegated first pass (4 of 5 agent batches; one batch re-run by hand after an infrastructure failure) with every finding re-verified in the source before acting on it. Fix-on-spot was applied whenever a change was small and testable; everything else went to TODO_LIST.md.

The headline find. The compression writer duplicated response bodies whenever a handler's Write chunking exactly filled the min-size buffer: the consumed branch of writeBuffered fell through with the payload still in the write argument, and the flush/stream step wrote it a second time. Not covered by 96.9% line coverage (the exact-fill boundary was never hit by an assertion), not caught by three prior reviews, not caught by lint, race, or fuzz suites — because no fuzz target ever decompressed the response and compared it. The new round-trip fuzz invariant found it in seconds, on the standard Accept-Encoding: gzip path with an exactly-minSize-byte body. This is the argument for execution-probe invariants over line coverage.

01Fixed On the Spot

CRITICAL compressWriter duplicated response bodies on exact buffer fill
compress_writer.go:127-151 (writeBuffered)

A Write bringing the buffer to exactly minSize copied the payload into the buffer but left it in b; the subsequent compress-and-stream (or plain-flush) wrote those bytes again. Any handler whose body chunks hit the boundary exactly served corrupted responses. Fixed by clearing the write argument in the consumed branch; regression test TestCompressWriter_ExactMinSizeWrite_IsNotDuplicated and a permanent fuzz seed.

MAJOR Recovery swallowed http.ErrAbortHandler
recovery.go

net/http's sentinel for "abort this response silently" was caught, logged as a panic with a stack trace, and answered with a 500 written to the already-aborted connection. Recovery now re-panics the sentinel unchanged (guarded type assertion so a non-comparable panic value cannot crash the comparison). Regression: TestRecovery_RepanicsErrAbortHandler.

MAJOR Double Close on a compressing writer panicked
compress_writer.go (Close)

Close nilled the writer but left compressing true, so a second Close dereferenced a nil interface. Unreachable through the middleware today, but a loaded gun for any future code path. Close is now idempotent on both the success and error paths, with two regression tests.

MAJOR Error templates claimed "zero disables the limit" twice
errors.go:296, errors.go:350

maxbodysize.max_bytes_negative said zero means unlimited (false: a zero MaxBytesReader rejects any non-empty body — verified by direct stdlib probe); decompression.max_size_negative said zero means no limit (false: zero selects the 16 MiB default). Same false-claim class the 2026-08-30 README fix addressed; the templates had been missed. Field docs now state the real semantics and a TestMaxBodySize_ZeroLimitRejectsNonEmptyBody execution-probe test pins them.

MAJOR Three tests verified nothing
compression_negotiator_test.go:154, etag_test.go:86, server_test.go:324

TestCompression_CustomFactory negotiated identity, which the middleware short-circuits before any factory lookup — the plugin path was never executed (now negotiates a real custom encoding and asserts the header); TestETag_WorksInMiddlewareStack checked only stack metadata without serving a request (now serves and asserts the ETag header); TestServerServesRequests called the handler directly instead of the running server (now binds a concrete port and issues a real HTTP GET).

NICE Negotiator tie-break overflow
compression_negotiator.go (nameOffset)

The base-256 byte-accumulation key for unknown encodings overflowed int at nine name bytes, making the documented deterministic order undefined for long custom encoding names. Replaced with a lexicographic rank; behavior change is limited to tie-break order among custom encodings.
